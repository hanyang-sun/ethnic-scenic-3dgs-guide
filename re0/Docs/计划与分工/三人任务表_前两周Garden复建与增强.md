# 三人任务表  Garden 复建与导览增强

本表执行《民族建筑景区3DGS项目计划书_三人小组完善版》第 1～2 周的桌面端目标。三人可以用 AI 生成代码初稿、解释 API 和排查报错；每人须亲自在复建工程中创建文件、配置组件、运行验证，并能说明自己负责模块的输入、输出和关键逻辑。以下按每人每天投入约 4～6 小时估算：**10 个工作日完成目标，另留 2～3 个工作日处理集成和目标电脑上的问题**。完整计划仍为 16 周；民族建筑素材替换、质量感知推荐和 VR 属于后续阶段。

## 四  文件归属与交接

文件名可以按代码实现微调，但主要职责不变。A 独占修改主场景；B/C 在自己的脚本和数据文件中开发，合并时由 A 将组件挂到场景并检查引用。

| 负责人 | 主要文件或对象 | 应能解释的关键问题 |
| --- | --- | --- |
| A | `Assets/Scenes/GardenPrototype.unity`、`Assets/GaussianAssets/Garden/`、`CameraController.cs`、步道与障碍 Collider、URP 配置、Windows 构建 | 3DGS 如何显示；相机位置如何对应模型；碰撞体为何要单独做；暂停和重置如何影响玩家。 |
| B | `POI.cs`、`POIManager.cs`、`DestinationSelector.cs`、`DistanceHUD.cs`、`ArrivalPanel.cs`、`RouteLine.cs`、建议新建 `TourMap.cs`、`TourControlsUI.cs`、`TourLog.cs`；景点数据与 UI 预制体 | POI ID 和坐标如何使用；地图坐标如何换算；访问计数如何避免重复；JSONL 每条事件表示什么。 |
| C | `RouteGraph.cs`、建议新建 `RoutePlanner.cs`、`ArrivalDetector.cs`；路点和连边数据 | Dijkstra 如何选路；障碍如何筛掉边；何时重规划；到达与“真正看清景点”有何区别。 |

### 三人先约定的接口

1. **A → B/C**：玩家 `Transform`、主相机、起点、`TourObstacle` 层、可走区域及 `scene_config_id`。坐标统一使用 Unity 世界坐标；没有可靠实地标定前，距离写“场景单位”。
2. **B → C**：稳定的 `poi_id`、名称、类别、说明、到达节点、范围和候选观察位置。改 ID 或节点时先通知 C。
3. **C → B**：`reachable`、`route_id`、`route_revision`、路线点、路线长度、当前状态及唯一的到达事件。B 用它画线、更新地图和写日志。
4. **日志字段**：至少包含 `schema_version`、`session_id`、UTC 时间、事件类型、玩家位置、相机姿态、目标景点 ID、路线 ID、路线长度、到达状态和场景配置 ID；暂未实现的研究指标写 `null`。到达事件只表示进入到达范围，不能写成“观看完成”。

## 五  AI 使用与个人验收

AI 可以给出初稿、报错解释、接口建议和测试步骤。每个负责人提交模块前，自己完成以下检查：

- 能指出脚本挂在哪个 GameObject，Inspector 中要配置哪些引用和数值。
- 能用自己的话说明关键方法的输入、输出、触发时机；能解释为什么需要该方法。
- Unity Console 无新增编译错误；进入 Play 实际操作一遍，并保存截图或日志。
- 在一条改动记录中写明：改了什么文件、如何测试、还有什么未解决的问题。

共同验收按计划书区分状态：**本组已验证**、**参考实现待移植**、**尚未实现**。`01_3DGS景区导览` 的现成演示程序不能当作复建工程的验收证据。每天下班前合并一次接口和场景引用；组长维护任务看板、记录阻塞项、组织 D5 和 D10 的联合演示。
