# Garden 原型：团队文件规范与协作说明

适用范围：当前 `ScenicTour-Garden` 技术原型及团队整合包。Unity 编辑器版本为 `6000.3.24f1`；团队包内嵌 UnityGaussianSplatting `1.1.1`，URP 为 `17.3.0`。这里的“归属”指维护责任，不代表文件的历史作者。

## 一、向组员解释：为什么会有这么多文件

用一条依赖链解释最容易理解：

```text
garden.ply（画面） + cameras.json（采集位置）
                    ↓ GardenImport.cs
garden.asset + 5 个 .bytes（Unity 可渲染资源）
                    ↓ GardenSetup.cs + SampleScene.unity
GardenPrototype.unity（可运行场景）
        ├─ CameraController + BoxCollider：可以走、不会直接穿透
        ├─ POI + RouteGraph + RouteLine：知道目标和路线
        └─ Selector + HUD + ArrivalPanel：能选择、看提示、看介绍

manifest.json / URP Renderer：保证插件和渲染功能能加载。
metadata.json：保留素材来源与交付说明，不参与当前运行逻辑。
GardenValidate.cs：检查上述各环节是否接通。
```

因此文件不是重复劳动，而是保存了四种不同东西：**原始数据、代码规则、Unity 生成结果、工程配置与证据**。3DGS 只有视觉信息；步道、碰撞、POI 和 UI 不能从 PLY 自动获得。

## 二、文件必要性和维护人

| 类别与路径 | 目的 | 维护人 | 是否由程序读取 |
|---|---|---|---|
| `SourceAssets/Garden/garden.ply` | 原始高斯模型；重新导入的输入 | A | 编辑器导入时读取 |
| `SourceAssets/Garden/cameras.json` | 185 个采集相机位姿；导入到模型资源，供初始视角和路点构建使用 | A 保管，C 使用位置信息 | 插件导入时读取 |
| `SourceAssets/Garden/metadata.json` | 来源、规模、划分、许可提示与已知限制 | A 保管，全组核对 | 当前代码不读取 |
| `Assets/GaussianAssets/Garden/garden.asset` 与同目录五个 `.bytes` | PLY 转换后的 Unity 3DGS 资源 | A 生成 | 渲染器运行时读取 |
| `Assets/Scenes/SampleScene.unity` | 场景生成脚本的底座，提供主相机和高斯渲染器 | A | 构建场景时读取 |
| `Assets/Scenes/GardenPrototype.unity` | 最终可运行场景，保存组件和引用 | A 负责合并，三人验收 | Play 时读取 |
| `Packages/manifest.json`、`ProjectSettings/`、URP Renderer Data | 固定 Unity 包、输入和渲染设置 | A | Unity 打开工程时读取 |
| `Assets/Fonts/`、`Assets/Resources/NotoSansSC SDF.asset` | 中文 TMP 文本资源 | B | UI 运行时读取 |
| `Preview/Garden.png`、验证日志、说明文档 | 展示与验收证据 | 对应模块负责人 | 不控制 Play |

只运行已生成场景时，`garden.ply`、`cameras.json`、`metadata.json` 不会在每一帧被读取；但要**从原始数据复建、核对来源或重新生成路点**，这些原始文件必须保留。`garden.asset` 与五个 `.bytes` 是一套资源，不应拆开复制。

## 三、源码归属

### A：场景与漫游

- `Assets/Editor/GardenImport.cs`：导入模型。
- `Assets/Scripts/Runtime/CameraController.cs`：视角、移动、加速与重力。
- `Assets/Editor/GardenCapture.cs`：场景预览图。
- `Assets/Scripts/Runtime/ProxyColliderBuilder.cs`：早期手动碰撞辅助工具；当前 Garden 场景不运行它。
- `Assets/Editor/GardenSetup.cs`：**A 作为主维护人**，负责合并 B/C 提供的场景参数，再生成最终场景。此文件涉及所有模块，改动前需让另外两人知道。

### B：界面与反馈

- `Assets/Scripts/Runtime/DestinationSelector.cs`：目标选择按钮。
- `Assets/Scripts/Runtime/DistanceHUD.cs`：方向与距离。
- `Assets/Scripts/Runtime/ArrivalPanel.cs`：到达介绍、关闭状态。
- `Assets/Scripts/Runtime/PrototypeFonts.cs`：中文字体加载。
- `Assets/Editor/GardenUiSettings.cs`：字号和界面尺寸。

### C：景点与导航

- `Assets/Scripts/Runtime/POI.cs`：景点数据结构；A/B 也依赖这个接口，修改字段要同步通知。
- `Assets/Scripts/Runtime/POIManager.cs`：景点列表和当前目标。
- `Assets/Scripts/Runtime/POILabel.cs`：三维景点标签。
- `Assets/Scripts/Runtime/RouteGraph.cs`：路网和最短路。
- `Assets/Scripts/Runtime/RouteLine.cs`：将路径画在场景中。

`Assets/Editor/GardenValidate.cs` 是**共同验收文件**：A 检查模型、相机和碰撞；B 检查字体、尺寸与弹窗；C 检查三个景点及路网。由 A 合并检查代码并运行最终验证。

## 四、目录和命名规范

1. **目录分层**：编辑器菜单和自动生成代码放 `Assets/Editor/`；Play 时执行的组件放 `Assets/Scripts/Runtime/`；原始 PLY/JSON 放项目根目录的 `SourceAssets/Garden/`；生成的高斯资源放 `Assets/GaussianAssets/Garden/`；场景放 `Assets/Scenes/`。不要把 PLY 误放进 `Assets`，当前导入脚本按项目根目录的相对路径查找它。
2. **C# 命名**：一个主要类对应一个同名 `.cs` 文件；类和公开方法用 PascalCase（如 `RouteGraph`、`TryFindPath`），字段与局部变量用 camelCase（如 `showDistance`、`currentIndex`）。文件名大小写保持一致。
3. **Unity `.meta`**：场景、脚本、字体、资产旁边的 `.meta` 必须与文件一起同步。Unity 用 GUID 维持引用；单独复制或重建 `.meta` 可能导致场景出现 Missing Script、资源引用丢失。
4. **生成文件**：`garden.asset`、五个 `.bytes` 和 `GardenPrototype.unity` 由工具生成。修改导入或构建逻辑时，先改源脚本再重建；已手工调整场景时尤其要注意 `GardenSetup.Build` 会覆盖最终场景。
5. **工程版本**：三人统一使用 Unity `6000.3.24f1`；团队整合包内的 3DGS 插件位于 `Packages/org.nesnausk.gaussian-splatting`。不要让成员各自安装不同版本的插件后再提交变更。

## 五、数据字段规范

- `POI.id` 使用稳定、唯一的英文小写标识，如 `view_west`；显示给玩家的中文名称放 `POI.name`。不要用名称代替 ID，因为文案可能修改。
- `POI.position` 和 `RouteGraph` 路点都是 **Unity 世界坐标**。Y 值应对应可行走地面。当前长度写“场景单位”，未校准为实地米数；汇报时不要直接称为“米”。
- `RouteGraph.edges` 的 `a/b` 是 `nodes` 数组索引；移动、删除或重排节点后，要检查全部边及三个 POI 的可达性。
- `POIManager` 当前的三个 Garden 景点由 `GardenSetup` 写入场景；`POIManager.PopulateDefaults()` 中的“入口/主展区/观景台”仅是通用占位数据。当前工程**没有读取 `pois.json`**，不要把新建 JSON 误当成已接入的数据源。
- `metadata.json` 保留上游原文。它记录约 **583 万点**的上游预训练模型，而当前实际导入的 `garden.ply` 是 **130 万点**；二者不要混写。模型点数以当前 PLY 和 `garden.asset` 为准。来源、许可、相机划分等字段若要修改，应附上对应来源依据。
- `cameras.json` 是采集位姿数据。不要为了调整步道直接改原始相机文件；在路点、模型变换或场景生成参数中处理，并保留原始数据供复核。

## 六、三人协作的最小流程

1. 各自在独立的脚本文件修改自己的模块；修改 `POI.cs`、`GardenSetup.cs`、`GardenPrototype.unity` 等共享接口或场景前先沟通。
2. B/C 提交对场景生成参数的需求，由 A 合入 `GardenSetup.cs`。三人不要同时重建或手工覆盖同一个 `GardenPrototype.unity`。
3. 同步工程时保留 `Assets` 与 `.meta`、`Packages`、`ProjectSettings`、必要的 `SourceAssets`。`Library`、`Logs`、`Temp`、`Obj`、`UserSettings` 是本机缓存或设置，交付时无需放入压缩包。若使用 Git，大型 PLY 与 `.bytes` 应使用适合大文件的存储方式。
4. 合并后运行 `Garden Prototype/Validate scene`，再进入 Play 人工走查：选择三个景点、观察路线、沿路行走、到达并关闭弹窗、离开返回后再次出现。
5. 提交说明至少写清：改了哪个模块、改动原因、影响了哪些文件、验证结果、是否重建了场景。

## 七、汇报时可直接这样说明

“我们把工程分成素材、场景、导航、界面和验证五层。A 负责把 Garden 高斯数据变成可见、可走的 Unity 场景；C 在可走范围上定义景点和路网、计算路线；B 将选择、距离、方向和到达介绍呈现给用户。`GardenSetup` 把三人的组件组装成场景，`GardenValidate` 检查集成结果。`metadata.json` 用于记录数据来源和限制，不参与运行时导航。所有人使用同一 Unity 与插件版本，并保留 `.meta` 文件保证引用一致。”
